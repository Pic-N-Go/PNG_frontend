# 신고 접수 및 관리자 처리 기능 스펙

## 1) 기능 정보

- 기능명: 게시글·리뷰 신고 접수 및 관리자 처리
- 담당자: 미지정
- 관련 이슈: 없음
- 관련 도메인: `report`, `admin`
- 대상 플랫폼: iOS / Android

## 2) 문제와 목표

- 해결하려는 문제: 사용자가 부적절한 게시글과 리뷰를 신고하고 관리자가 한 화면에서 조회·처리할 수 있어야 한다.
- 사용자 가치: 신고 사유와 상세 내용을 안전하게 전달하고 운영 결과를 일관되게 관리할 수 있다.
- 완료 기준: 게시글·리뷰 신고 접수부터 관리자 조회, 기각, 대상 삭제, 처리 메모 저장까지 실제 API로 동작한다.

## 3) 범위

- 포함(In Scope):
  - 게시글 및 리뷰 신고
  - 공통 신고 사유·상세 입력 바텀시트
  - 관리자 통합 목록과 상태 필터
  - 신고 상세 조회
  - 처리 메모를 포함한 기각 및 대상 삭제
- 제외(Out of Scope):
  - 댓글 및 채팅 신고
  - 신고자가 자신의 처리 이력을 조회하는 화면
  - 관리자 대시보드 이외의 별도 관리자 앱

## 4) 사용자 시나리오

- 시나리오 A — 사용자 신고:
  - Given: 로그인한 사용자가 다른 사용자의 게시글 또는 리뷰를 보고 있다.
  - When: 신고 사유를 선택하고 선택적으로 상세 내용을 작성해 제출한다.
  - Then: 신고 API가 호출되고 성공 토스트가 표시된다.
- 시나리오 B — 관리자 처리:
  - Given: 관리자가 처리 대기 신고의 상세 화면을 열었다.
  - When: 기각 또는 대상 삭제를 선택하고 처리 메모 모달에서 확정한다.
  - Then: 상태와 처리 메모가 저장되고 관련 신고 목록이 갱신된다.

## 5) UI/UX 요구사항

- 참조 목업 파일: `src/components/ui/community/community-post.html`
- 목업과의 차이: 목업의 사유 선택 즉시 접수 대신, 사유 선택 후 상세 내용을 입력하는 2단계 흐름을 사용한다.
- 화면 전환 규칙: 리뷰 액션시트를 닫은 후 신고 바텀시트를 열어 시트가 겹치지 않게 한다.
- 빈 상태/에러 상태: 관리자 목록에 빈 상태를 표시하고 조회 실패 시 재시도 진입점을 제공한다.
- 로딩 상태: 신고 제출·관리자 처리 중 중복 실행을 막고 진행 표시를 제공한다.
- 파괴적 동작: 기각과 삭제 모달에 되돌릴 수 없다는 안내를 표시한다.
- 접근성: 필터, 상세 진입, 닫기, 처리 버튼 및 메모 입력란에 접근성 레이블을 제공한다.

## 6) 데이터/API 요구사항

- 사용자 API:
  - `reportApi.reportPost()` — `POST /reports/posts/{postId}`
  - `reportApi.reportReview()` — `POST /reports/reviews/{reviewId}`
- 관리자 API:
  - `adminApi.getReports()` — 전체/대기/완료/기각 목록, 페이지당 10개
  - `adminApi.getReportDetail()` — 신고 상세
  - `adminApi.processReport()` — 기각과 처리 메모 저장
  - `adminApi.deleteReportedTarget()` — 대상 삭제와 처리 메모 저장
- 핵심 필드: `reason`, `detail`, `targetType`, `status`, `targetContentSnapshot`, `resolutionNote`, `handledById`, `handledAt`
- 실패 처리 방식: API 오류 메시지를 토스트로 표시하고 성공 전에는 모달과 시트를 유지한다.
- 캐싱 전략: 관리자 처리 성공 후 `['admin', 'reports']` 하위 쿼리를 무효화한다.

## 7) 상태 관리

- 서버 상태: TanStack Query의 `useQuery`와 `useMutation`
- 로컬 UI 상태: 컴포넌트 `useState`로 선택 사유, 입력 내용, 필터, 페이지, 모달 상태 관리
- Zustand: 인증 토큰과 현재 사용자 정보만 사용
- 영속화 필요 여부: 없음

## 9) 수용 기준

- [x] AC1: 게시글과 리뷰에서 동일한 신고 바텀시트를 사용해 실제 신고 API를 호출한다.
- [x] AC2: 관리자가 전체, 처리 대기, 조치 완료, 신고 기각 목록을 10개 단위로 조회한다.
- [x] AC3: 관리자가 신고 상세와 신고 당시 원문을 확인한다.
- [x] AC4: 관리자가 처리 메모를 남기며 신고를 기각하거나 대상을 삭제한다.
- [x] AC5: 처리 성공 후 관련 관리자 신고 쿼리가 갱신된다.

## 10) 테스트 시나리오

- 정상: 게시글 신고, 리뷰 신고, 필터 전환, 페이지 이동, 상세 조회, 메모 포함 기각·삭제
- 경계: 상세 내용 500자, 처리 메모 1,000자, 빈 메모, 마지막 페이지
- 실패: 인증 만료, 중복 신고, 이미 처리된 신고, 삭제 대상 없음, 네트워크 오류
- 수동 확인 필요: 360dp와 430dp의 필터·모달 배치, 키보드 표시 시 처리 버튼 접근성

## 11) 결정 사항

- 댓글과 채팅 신고는 백엔드·프론트 모두 후속 범위로 둔다.
- 관리자 삭제는 같은 대상을 가리키는 모든 대기 신고를 함께 완료 처리한다.
- 처리 메모가 없는 삭제는 백엔드 기본 문구를 사용한다.
